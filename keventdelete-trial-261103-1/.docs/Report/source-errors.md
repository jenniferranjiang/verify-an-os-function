# KEventDelete 当前源码问题

2026-11-03 独立 C 分析。依据当前权威 `Ubiquitous/XiZi_IIoT_Macro/kernel/thread/event.c`（SHA256 `1351dfb28f28413e50790fd4390777e647c6d60f1fe9debf850367c902841d64`）、非 SMP 的32位验证配置。以下是具体可达的静态交错反例，没有声称做过目标板运行或动态复现。没有修改源码，也没有继承旧实验的使用约束；下述限制来自本轮用户的明确批准。

D1、D2均直接发生在本轮目标KEventDelete的删除路径上。用户现已明确批准**通过环境前提排除D1/D2，不修复源码**，并确认输入范围 **0 <= id < 65536**。按最新reporting-guide的“新增假设”条款，本轮仅在这些条件下继续原C的设计与审阅；原缺陷仍存在，未应用修复patch，也未获得实现验证阶段批准。

实际采用的范围应在正式设计中可追踪地表达：查找得到目标对象后，环境不能在本次删除取得其回收所有权之前删除或释放该对象（排除D1）；pending检查/清空到目标注销期间，环境不能向该对象加入新等待者（排除D2）。它们是对本次目标对象生命周期及等待队列的环境约束，不是“非SMP天然安全”，也不意味着其他Event API已正确。输入上界不是ID_NUM_MAX：128..65535仍合法进入本轮范围，并按IdGetObj容量检查走未命中返回；65536及以上、负ID不在当前批准规格的调用范围。正式设计须核对其环境关系确实覆盖该约束，不可只写一条无约束能力的注释。

## D1：查找结束后对象可以先被另一个删除释放

状态：已确认，源码未修复；用户批准以本次删除期间的对象生命周期环境前提排除触发场景，仅在该前提下继续。

位置：`event.c:258`调用FindEventById；该函数`220–228`锁内查找并在`228`解锁，`230`返回裸指针；`263`分派_EventDelete；首次实际对象读取位于`62`的IsDoubleLinkListEmpty中（`double_link.c:94–96`读取node_next）；随后`68/70/73`分别访问ID、管理link和释放对象。

最小场景：事件ID j有效、对象地址p、pending为空；A、B都是普通任务，进入API时无外层临界区。

| 步骤 | 执行 |
|---|---|
| 1 | A调用KEventDelete(j)，FindEventById在锁内取得p，在event.c:228解锁。 |
| 2 | A在继续删除前被抢占。B调用KEventDelete(j)，正常完成清空检查、ID注销、管理链摘除和event.c:73的x_free(p)。 |
| 3 | A恢复，持有的局部p未更新。NULL_PARAM_CHECK只检查非空，p仍非空。 |
| 4 | A在event.c:62读取p->pend_list.node_next，读取已释放对象；后续还可能再次释放或破坏已重用内存。 |

预期：两个删除竞争时，一个完成删除，另一个发现不存在或拥有足以保证对象存活的权限。实际查找锁仅保护取得地址的瞬间，不能为后续访问提供生命周期。

仅给第62行读取加临界区仍不足：B可在该读取锁之前完成释放。非SMP也允许上述临界区之间的抢占。重新取得锁不会让已释放p恢复存活。

## D2：检查或清空pending后，新等待者仍能进入，随后对象被释放

状态：已确认，源码未修复；用户另行批准排除检查/清空到注销期间新增等待者的环境前提，仅在该前提下继续。单独禁止两个Delete并发原本不足以排除此问题。

位置：`event.c:62–65`检查/唤醒与`67–73`注销/释放分属不同阶段。LinklistResumeAll在`linklist.c:118–129`只为自身清空过程加锁，返回后不延长该锁。Process在`event.c:158–187`的临界区内，`182`可向仍发布的Event插入等待任务。

最小场景：有效事件E，FIFO/PRIO等待策略、初始events=0、pending为空；D正在删除，T是另一个正常可运行任务。

| 步骤 | 执行 |
|---|---|
| 1 | D已取得E，在event.c:62观察pending为空，因此不调用ResumeAll且resched保持0。 |
| 2 | D在event.c:67加锁前被抢占。 |
| 3 | T使用同一仍有效ID调用KEventProcess(id,1,EVENT_AND,1000,NULL)，查找成功；事件不满足，在event.c:182挂起并进入E的pending；选择KTaskSetDelay成功路径，在185建立正常超时，然后187解锁、189调度。 |
| 4 | D恢复，在67加锁，68注销ID，70摘除全局管理link，71解锁，73释放E。没有再次检查或唤醒T。 |
| 5 | T的sched_link仍链接到已释放的E->pend_list；后续正常超时唤醒在摘除该节点时可通过DoubleLinkListRmNode写入已经释放的哨兵。即使尚未触发该写，删除返回时仍遗留引用被释放对象的等待任务。 |

预期：删除应处理删除事务内属于该对象的等待者，移除全部共享引用后才释放。实际处理的是较早时刻的pending，随后仍允许新增等待者。初始pending非空时，ResumeAll返回后的窗口同样可以出现新等待者。

按源代码处理给IsDoubleLinkListEmpty单次共享读取加锁，只缩短读取自身窗口，步骤2仍存在。不能以该规则为由把查找、清空和注销合并为一个跨函数事务并称其为源码等价适配。

## D3：正int32 ID窄化为uint16，可能删除不同编号的事件

状态：源码行为已确认，用户已明确将本轮输入限制为0 <= id < 65536，故窄化反例不属于本轮批准范围。未修改源码，也未为范围外输入承诺无操作。

`event.c:218`只拒绝负数；`221`把int32 id传给`id.c:122`的uint16参数，因此65536变成0。若事件0存在，`KEventDelete(65536)`会查到并删除事件0。IdGetObj内部检查的是转换后的值，无法拒绝原始65536。KEventDelete的void返回类型没有错误值，但可以选择显式无操作策略。

这不依赖并发。若目标要求int32全域按编号查询并拒绝无效ID，应在窄化前检查范围。若用户明确选择只接受合法ID或保留低16位查找行为，规格须清楚说明；不能由agent自行加强Require。D1/D2在合法ID下仍存在，解决D3不消除它们。

## 用户已作出的决定及保留的修复参考

用户选择以环境假设排除D1/D2，并限制0 <= id < 65536；**没有选择或授权应用源码修复候选**。以下为此前提供的方案对照，仅保留修复参考，不再作为待答问题：

1. 授权修复目标删除事务。可参考当前真实SemaphoreDelete：让内部删除以ID为入参，在同一锁内查找、处理pending、注销ID和摘管理link，解锁后释放，再按需调度；同步EventDoneType和dispatch。还要处理已在锁外拿到p的Trigger/Process，否则仅修改Delete不能保护其他API的旧裸指针。若只修改目标，必须明确配套生命周期使用条件，不能声称整个Event并发接口安全。
2. 明确限定环境，使目标对象在本次KEventDelete从入口到返回期间不被其他任务删除、使用或加入新等待者；允许入口已有等待者并由本次删除唤醒。本轮用户已经批准D1/D2环境排除及0 <= id < 65536；正式模型应表达批准的必要约束，不擅自把它加强为所有OS状态完全不变。此路线不是源码修复，也不证明任意并发环境安全。

若只是把修复放到trial，应将结论标明对应修复候选，不说权威源码已修复。任何批准后的实际改动须重新核对路径/闭包并检查受影响部分。

## 未应用修复候选的独立结构审阅

审阅对象：[proposed-event-delete-fix.patch](proposed-event-delete-fix.patch)、`checks/proposed-fix/event.c`和`xs_event.h`。这是源码候选的结构检查，不是predicate/spec review-passed或实现证明；权威源码没有应用此patch，D1/D2源码层面仍未修复；本轮后续走已批准环境约束路线，该patch不作为活动验证输入。

候选把内部_EventDelete改成int32 id入参，public KEventDelete直接传id；锁在查找之前取得，贯穿pending检查、ResumeAll、ID注销、管理链摘除，之后才解锁和free。该结构关闭上述特定D1/D2交错：两个Delete不能同时在锁外持有已查询指针；Delete检查空pending之后，Process不能在该删除事务中插入waiter。LinklistResumeAll内部锁在该调用场景成为真正嵌套锁，非SMP保存/恢复中断状态的实现允许此嵌套，源码切片才可按既有规则去掉该层锁。

核对保留的行为：负ID在加锁前返回；查找未命中时解锁后返回；ID仍在IdGetObj调用处转uint16，D3的65536→0行为没有被这个候选修复或隐藏；pending非空仍设置resched并把旧等待者的exstatus设为-ERROR且唤醒；IdRemoveObj/管理摘链顺序不变；free与DO_KTASK_ASSIGN都在解锁之后。删除节点不再可由后来的ID查询取得后，释放前的抢占不会让另一个新Delete拿到同一个旧对象；ID复用后查到的是新对象，这是ID接口的一般代际问题，不是重复释放旧对象。

public `void KEventDelete(int32 id)`签名不变。内部_EventDelete与EventDoneType.EventDelete函数指针从Event*改为int32；在当前Ubiquitous/XiZi_IIoT_Macro源码树搜索，EventDoneType只由该header与event.c中的静态done使用，初始化和调用已同步。改变的是内部函数表的参数类型，需相关翻译单元重编译，不是保持所有内部接口完全不变。

保留风险：Trigger/Process仍调用FindEventById并在解锁后持有裸p。若它们在删除事务开始之前已取得p，删除仍可释放对象，随后它们访问p；Process甚至可在对象释放后尝试加入等待链。候选只关闭Delete自身“查找到使用”和“检查到注销”的事务窗口，不能声称整个Event模块任意并发调用安全。若要将“所有旧等待者处理后无人再引用”提升为真实系统保证，还须统一其他API的生命周期方案或取得明确使用约束。

主agent留下的patch dry-run与GCC 32位strict语法结果已查看：检查针对完整候选header及抽出的改动函数体，不能扩称整个内核构建通过。没有更小且同样清楚保留锁外free/调度的直接方案：仅在public函数外层加锁会让旧_EventDelete的free和调度在外层锁内执行，改变要求并需要额外拆分，因此当前ID入参候选更易审查。
