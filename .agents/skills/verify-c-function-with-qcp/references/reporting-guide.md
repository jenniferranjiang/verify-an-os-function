# 验证记录指南

报告首先写给用户看，其次才是留给工具和后续验证者的证据。默认不使用模板；根据当前问题选择最容易理解的结构。

## 写作原则

开头先用简明中文回答三件事：

1. 当前结论是什么；
2. 这对验证结果有什么影响；
3. 用户现在需要决定或关注什么，没有需要时明确写“无需用户操作”。

之后再给设计解释或技术证据。避免在开头堆路径、hash、symbol、revision 和 QCP/Rocq 内部术语；这些放在“证据”或附录。必须使用术语时，第一次出现用一句话解释。不要中英混排可以直接说清的内容，不写空栏目、`N/A`、长命令输出或逐文件成功清单。

结构由内容决定。无论怎样组织，都要让读者容易找到结论、依据、未解决问题和下一步。

## 必须保留的信息

不用固定标题，但每份记录要能看出：

- 记录在说哪个函数、模块或产物；
- 结论适用于哪份源码、配置和 formal revision；
- 结论依据是什么，必要时如何复现；
- 还有哪些 blocker、`[OPEN]`、源码错误或设计变更；
- 结论的边界以及下一步。

源码错误报告和设计变更记录使用稳定 ID，方便跨报告跟踪。其他元数据只在项目工具确实需要时添加。

## 先归因，再决定写什么记录

一次 parser、symbolic、VC 或 proof 失败只是症状，不能直接称为源码错误，也不一定需要设计变更。按最早根因分为四类：

1. **源码错误**：当前配置下的权威 C 本身违反明确的功能、安全、资源或并发要求，而且该判断不依赖“当前 proof 写不出来”。创建源码错误报告。
2. **设计变更**：predicate、spec、ownership、抽象状态、正式接口或其他已审阅设计必须改变。创建设计变更记录，并按影响范围使旧 review 失效。
3. **验证实施问题**：只需修改 annotation、strategy、辅助 lemma、tactic、构建配置或命令，已批准 formal 语义不变。不单独建立源码错误报告或设计变更记录；在当前工作状态和最终有效检查中说明即可。
4. **工具问题**：确认是 QCP、Rocq 或验证框架缺陷。标记为工具问题并保留复现证据；除非它同时证明 C 或 formal 设计有问题，否则不归入前两类。

如果根因还不明确，标记 `[OPEN]` 并继续诊断，不提前创建“源码错误”结论。源码行为是否违反要求本身不明确时，请用户确认需求。

## 各类记录

### Predicate 设计记录

说明当前有效设计，而不是记录整个工作过程。读者应能理解目标和边界、C 对象如何对应抽象状态、谁拥有内存、对象怎样建立/变化/失败回滚/删除、对外提供什么接口，以及仍有哪些限制。

具体字段地址和 formal 定义留在相邻 `.v` 注释中。逐轮审阅史放在 review，已批准设计的变化放在设计变更记录；设计正文只保留理解当前设计真正需要的决定和链接。

### Review 记录

先给审阅结论和是否阻塞，再解释审阅了哪个 revision、哪些范围、发现了什么。Issue 要说清“哪里不一致、会造成什么后果、怎样才算修好”，并标明它属于源码错误、设计变更、验证实施问题、工具问题还是仍待归因的 `[OPEN]`。

`affected-only` review 还要说明为什么只检查这些部分，以及影响范围如何确定。

### 设计变更记录

只在已审阅或已批准的 formal 设计需要变化时创建，使用 trial 内唯一 ID，如 `DCHG-20261011-01`。记录放在 `.docs/Report/design-changes/YYYY-MM-DD-N-<short-slug>.md`。

用简短文字说清：为什么必须改、从什么变成什么、影响哪些已批准内容、哪些接口或语义保持不变、需要重审或重跑哪些部分、当前批准状态。设计变更可以由 proof-discovered mismatch、源码/config revision 变化或源码错误触发；只有最后一种情况才链接源码错误报告。

### Final integrity 记录

先给 `verified|not-verified|partially-verified` 结论和剩余风险，再汇总当前有效检查：源码等价性、symbolic、VC/goal 计数、Rocq proof/compile、完整性和 trust scan。按需列出未解决的源码错误、待批准设计变更或实施 blocker；不复制完整诊断历史。

## 源码错误报告

源码错误报告只描述权威 C 中的缺陷，不用来收集所有验证失败。证明失败本身、predicate/spec 写错、annotation 不足或工具命令失败，都不是源码错误证据。

创建报告前必须确认：

- 问题存在于当前配置实际采用的权威 C，而不只是 annotated copy、旧 revision 或错误构建配置；
- 有明确要求说明“正确行为应是什么”；
- 能从 C 路径和状态变化说明实际行为如何违反该要求；
- 已排除 formal model、spec、ABI 假设或工具解释错误是更早根因。

典型源码错误包括可达的非法内存访问、未定义行为、资源泄漏、错误回滚、返回值或状态转换违反明确 API 要求，以及破坏已确认并发/生命周期约束。若只能说明“当前 contract 证明不了”，应保持 `[OPEN]` 或转为设计变更，不能报告源码 bug。

报告放在 `.docs/Report/source-errors/YYYY-MM-DD-N-<short-slug>.md`，使用 trial 内唯一 ID，如 `SRCERR-20261011-01`。同一源码根因更新同一记录。

开头先说明：源码哪里错了、什么场景会触发、有什么后果、是否阻塞当前验证、需要用户决定什么。技术部分再给权威源码位置、激活配置、触发路径、预期与实际行为、影响范围、最小复现或反例，以及可能的源码修复方向。

未经用户授权不得修改权威源码。源码错误若与批准 contract 冲突，相应验证结论不能标为 `verified`；如果用户改为验证“源码实际行为”，应先形成新的设计变更并重新审阅，不能静默弱化 spec。

状态可使用 `open|confirmed|source-fixed|accepted|superseded`。`source-fixed` 记录源码 revision 和复测证据；`accepted` 记录用户决定及仍然存在的风险。

## 链接和旧记录

Review/final 链接相关 `SRCERR` 或 `DCHG`，源码错误报告与设计变更记录反向列出受影响 revisions。Final integrity 为 `verified` 时，不得存在与批准目标冲突的未解决源码错误或未批准设计变更。

旧报告不因本规则强制重写。下一次有实质更新时再采用新分类；不要为了迁移格式改变 formal revision 或触发重审。
