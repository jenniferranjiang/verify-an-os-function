# 验证记录指南

报告首先写给用户看，其次才是留给工具和后续验证者的证据。以下是内容分类，不是每次任务都要生成的文件清单。按实际需要组织，可合并在同一文件中；优先更新已有内容，同一事实只记录一次。过程报告不强制模板、固定文件名或空栏目；最终报告采用下文的默认位置或工程已有布局。

## 写作原则

面向熟悉 C 和目标模块、但未参与本次证明的读者，按当前要解释的设计或问题组织记录，并标明相关文件、函数或定义的位置。用自然语言说明这里做了什么、为什么这样设计，或发现了什么问题及其影响。尚未确定的内容直接说明哪里不清楚、缺什么依据、准备如何确认。

技术术语用于精确定位，不能代替解释。例如 ownership 要说明谁持有哪块内存、何时交出或收回；dependency closure 要说明此次修改具体影响哪些定义或调用者、为什么。不要只写“资源不闭合”“模型不一致”或“检查通过”，而不解释缺少什么、哪里不同或检查支持什么结论。

例如，假设审阅发现删除操作的内存归还没有被描述，与其写“lifecycle ownership 不闭合，需 invalidated dependency closure”，可以写：“删除函数会释放信号量对象，但当前描述没有说明该对象的内存如何归还给分配器，因此还不能用它验证删除操作。需要补充这一步资源转移，并重新检查依赖这一描述的删除函数约定。”这只是表达示例，不代表项目中存在该问题；实际记录还应附对应位置和证据。

位置可写成文件链接及行号，或文件路径和函数/定义名，可以适当引用源代码。这次审阅针对哪一份代码、哪些编译选项，以及哪一版 predicate/spec在结论处注明一次即可。

## 存放与生命周期

`.docs/Report/` 不是工具工作区。报告引用正式文件、当前 revision manifest 或 controller 的最终结果，不复制它们的全文。运行中的控制器状态留在工具管理的原生路径；编译缓存、重复 VC、过期快照、一次性脚本和中间日志放在任务专用 `/tmp` 目录，阶段结束后清理。

同一事实出现新 revision 或新状态时，更新已有记录或明确标出历史版本，不让旧文件继续伪装成当前状态。完成 `final-check` 及正式成果迁出检查后，按下节整理能定位冻结输入、最终结果、源码对应和信任边界的紧凑证据；不再将每个 claim、finalize 或 step 回执另存到 `.docs/`。对仍在运行或可能恢复的 workflow，不提前删除 controller 自己管理的状态。


## 完成后保留什么

完整验证及全局迁出检查结束后，默认只维护一份最终报告，放在全局 `.docs/Report/<module>/<function>.md`（已有报告布局可沿用）。把过程记录中仍影响最终结论的内容归入这份报告，不按实验轮次保留整套报告或 trial 快照。

最终报告保留验证对象、源码版本和配置、最终 predicate/spec revisions、审阅与 controller/final-check 结论、信任假设及适用限制，以及正式 lib、annotated C、VC 的位置和必要版本对应。用足以理解结论的摘要，不复制完整源码、证明或工具日志。

- 设计草稿、历次审阅意见、设计变更过程及已解决的工具错误：将影响最终结论的内容归入最终报告，其余删除。
- 编译日志、逐步 claim/finalize/step 回执、重复状态记录和旧工作区：检查结果摘要保留后删除，不把临时日志作为最终报告的唯一证据。
- 已确认的源码缺陷及其修复/授权记录：独立保留在全局报告目录，由最终报告引用；不能当作已解决的工具错误一并清掉。
- 本轮未解决的问题或尚未完成的工作：保留记录及恢复所需输入，不以报告精简为由删除。

仅在工具确实需要机器可读的哈希或版本映射时另留 manifest；否则这些信息写入最终报告即可，不重复维护两套记录。历史版本通过项目版本管理追溯，不默认复制多份完整产物。记录安置、链接检查和删除时机统一按主 skill 的[收尾流程](../SKILL.md#正式成果迁出与-trial-删除)执行。

## 各类报告

以下说明各类报告的用途与必要内容，不要求固定章节或空栏目。

### Predicate 设计报告

解释当前设计如何描述 C 对象的内存分布和行为，以及为什么这样组织。

### Spec 报告

Predicate/spec 均达到 `review-passed` 后、请求用户确认 revisions 前，更新这份报告并提供链接；仅设计审阅的任务也提供导读，不因此请求启动实现证明。报告开头简短标明对应的 predicate/spec revisions，正文突出需要用户重点判断的具体内容：

- `Require` 限制了哪些输入和状态，是否排除了应覆盖的真实路径。
- `Ensure` 如何描述成功、失败和部分成功的结果，返回值、资源和模块状态如何变化。
- 模块状态与 `os_inv` 的关系：资源由谁持有，何时加入或移出系统不变量。
- 值得人工判断的抽象、源码适配和结论限制。

每项给出文件链接及具名 spec/定义/分支位置，解释当前规格实际表达的含义，以及值得用户确认的问题；按当前函数的重要性选择和排序，不机械填满四类（这四类只是一个举例），不只罗列通用检查项。涉及关键路径时，指出对应的具体条件或后置分支，不能仅说“已覆盖失败路径”。

相关设计改变后同步更新定位和含义，避免导读与待确认 revision 不一致。最终收尾时仅将仍影响结论的内容汇入最终报告。

### 审阅报告

说明review了哪个版本、结论是什么；发现问题时，标出位置，解释哪里不一致、有什么影响以及如何确认修复有效。Predicate 和 spec 分别给出结论，可写在同一份报告中。

原因尚不清楚时直接解释疑点及所缺依据。如果没有改变 predicate/spec 的含义，只是补充或调整证明步骤、修正工具用法，有必要时简要说明即可，不必另写报告。已有问题说明直接引用位置或 ID。

### 错误报告

仅记录当前配置下权威 C 源码本身的缺陷。Predicate/spec 写错、证明未完成、注解不足、编译或工具失败等验证过程中的问题，不属于此类报告。发现源码错误时应该填写报告，并主动在对话中报给用户。

报告中需要包含：
指出源码位置，最好给出链接，用具体触发场景解释预期行为、实际行为和后果，并附支持判断的执行路径或反例以及可能的修复建议。权威源码 `source_root` 只读；修复补丁以当前 trial 的 `annotated_C/` 副本为应用目标，不能因用户批准修复而回写原仓库。

每项问题须分别记录原源码与验证副本的状态及解决依据：副本已修复的注明原文件路径与基线 revision/hash、补丁或差异、修复后的副本路径与 revision/hash，以及针对性检查结果，状态写为“验证副本已修复，原源码缺陷仍存在”；查证并非缺陷的注明源码/配置证据。尚未查证的疑点明确标为待查证，不冒称已确认缺陷，也不当作已解决。报告中明确未解决项阻塞 predicate/spec 编写及后续流程，不能只列“已知限制”后继续给出通过结论。

### 源码问题门禁

已发现的源码问题必须先明确解决，否则不得开始或继续编写、修改 predicate 和 spec。

用户批准的修复已应用于验证副本并通过针对性检查后，即可针对该修复版本解除门禁；不要求修改原仓库。后续 C 分析、predicate/spec、实现证明及最终报告均以同一副本 revision 为对象，同时保留原源码基线与修复差异。源码一致性检查须区分批准的缺陷修复、规则允许的适配和其余应保持一致的代码，不把修复版本的结论套用到原源码。

已产生的设计产物保留，但暂停设计及后续推进；待审候选标为 `needs-fix`，受问题影响而不再成立的已通过结论标为 `invalidated`。问题未解决时，不得给出新的 `review-ready`/`review-passed` 结论、合并待审设计或进入实现证明。问题解决后，更新源码/配置依据和切片，重新分析受影响范围，再恢复设计、编译及必要的重审。

若用户批准修复验证副本或增加假设，须在对应错误报告中记录批准的具体内容及实际处理结果：副本修改说明修改位置、原代码和修改后代码；新增假设写明具体内容、适用范围，以及对验证结论的限制。通过假设排除错误触发场景时，应明确源码缺陷仍然存在，仅在该假设下继续验证，不得标为源码已修复。

经用户批准修改验证副本时，在副本中注释保留原出错代码，而不是直接删除；注释可标明这是 bug 修复。正式成果迁出时保留修复差异和结论范围，仅迁入验证工程的全局 annotated C，不向 `source_root` 应用补丁。

### 设计变更报告

用于说明已通过审阅或经用户批准的 predicate/spec 的含义发生的变化。尚未通过审阅的草案直接修改；仅调整文字、格式或证明步骤，不需要写设计变更报告。
说明为什么需要修改、原来如何描述、现在改成什么，以及影响哪些已有结论、需要重新审阅或运行哪些检查。相关内容可写在已有报告中，不必单独新建文件。

### 最终报告

引用 QCP controller 的实际状态及已有 final-check 结果，说明哪些目标已验证、哪些尚未验证及剩余限制，并给出 `verified|not-verified|partially-verified` 状态；未到 done 时如实说明尚未完成。到 done 后，记录正式 lib、annotated C、VC/证明迁入全局目录的版本对应，以及全局路径下的编译、引用和源码一致性检查结果。迁出或检查尚未完成时，不得报告整个流程已经结束。

VC 证明完成后、迁出整理前，在最终报告中附一项代码增量统计：对 `*_proof_manual.v` 和本轮修改/新增的 lib 文件，按文件列出新增、删除、净增行及两类合计，使用包含注释和空行的普通 diff。以修改前记录的实际版本为基线，新文件以空文件为基线；注明基线与统计终点，不将复制的原内容、未修改库或迁移调整计入增量，共享文件只计一次。缺少可靠基线时明确说明，不能用 HEAD 代替未提交的原始内容或估算数字；新 manual 的模板行包含在文件增量中，不代表手写证明量。未完成时的统计标为阶段性数据，不另建统计报告。

最终完整性结论写入这份最终报告，不额外保留另一份重复的完整性报告。原设计与审阅结论的必要内容汇入其中（trusted函数，全局假设等），源码缺陷报告保留；迁出检查与 trial 删除按主 skill 的[收尾流程](../SKILL.md#正式成果迁出与-trial-删除)执行。
