# 验证记录指南

报告首先写给用户看，其次才是留给工具和后续验证者的证据。以下是内容分类，不是每次任务都要生成的文件清单。按实际需要组织，可合并在同一文件中；优先更新已有内容，同一事实只记录一次。过程报告不强制模板、固定文件名或空栏目；最终报告采用下文的默认位置或工程已有布局。

## 写作原则

面向熟悉 C 和目标模块、但未参与本次证明的读者，按当前要解释的设计或问题组织记录，并标明相关文件、函数或定义的位置。用自然语言说明这里做了什么、为什么这样设计，或发现了什么问题及其影响。尚未确定的内容直接说明哪里不清楚、缺什么依据、准备如何确认。

技术术语用于精确定位，不能代替解释。例如 ownership 要说明谁持有哪块内存、何时交出或收回；dependency closure 要说明此次修改具体影响哪些定义或调用者、为什么。不要只写“资源不闭合”“模型不一致”或“检查通过”，而不解释缺少什么、哪里不同或检查支持什么结论。

例如，假设审阅发现删除操作的内存归还没有被描述，与其写“lifecycle ownership 不闭合，需 invalidated dependency closure”，可以写：“删除函数会释放信号量对象，但当前描述没有说明该对象的内存如何归还给分配器，因此还不能用它验证删除操作。需要补充这一步资源转移，并重新检查依赖这一描述的删除函数约定。”这只是表达示例，不代表项目中存在该问题；实际记录还应附对应位置和证据。

位置可写成文件链接及行号，或文件路径和函数/定义名，可以适当引用源代码。这次审阅针对哪一份代码、哪些编译选项，以及哪一版 predicate/spec在结论处注明一次即可。

## 存放与生命周期

`.docs/Report/` 不是工具工作区。报告引用正式文件、当前 revision manifest 或 controller 的最终结果，不复制它们的全文。运行中的控制器状态留在工具管理的原生路径；一次性编译实验的输出、重复 VC、过期快照、一次性脚本和中间日志放在任务专用 `/tmp` 目录，阶段结束后清理。当前工程供编辑器加载和增量编译使用的产物保留在构建配置指定位置，遵循主 skill 的[保留边界](../SKILL.md#临时产物与保留边界)，不作为阶段临时文件删除。

同一事实出现新 revision 或新状态时，更新已有记录或明确标出历史版本，不让旧文件继续伪装成当前状态。完成 `final-check` 及全局一致性检查后，按下节整理能定位冻结输入、最终结果、源码对应和信任边界的紧凑证据；不再将每个 claim、finalize 或 step 回执另存到 `.docs/`。对仍在运行或可能恢复的 workflow，不提前删除 controller 自己管理的状态。


## 完成后保留什么

每轮报告默认按“模块 / 日期与目标函数”组织：`.docs/Report/<module>/<YYYY-MM-DD>-<目标函数>/`。日期使用本轮开始日期，多个主目标可以并列命名，例如 `dataqueue/2026-11-16-InitDataqueue-DataqueuePeak/`；必要callee在报告正文中列明。用户指定及项目已有约定优先。

设计说明在该目录内使用 `design.md`，随本轮改动更新，实验或完整验证结束后长期保留。后续新一轮工作使用对应的报告目录，并可引用前一轮仍有效的设计解释。

完整验证及全局一致性检查结束后，验证结果整理为同一报告目录中的最终报告。它记录验证结论并引用设计说明，设计说明继续独立保留。

最终报告保留验证对象、源码版本和配置、最终 predicate/spec revisions、审阅与 controller/final-check 结论、信任假设及适用限制，以及正式 lib、annotated C、VC 的位置和必要版本对应。用足以理解结论的摘要，不复制完整源码、证明或工具日志。

- 设计说明：保留各轮有效的lib/spec/VC改动解释及规格审阅重点，完成后继续维护，最终报告引用这份说明。
- 历次审阅意见、已被替代的草稿和已解决的工具错误：将影响验证结论的内容归入最终报告，再清理过期过程记录。
- 编译日志、逐步 claim/finalize/step 回执、重复状态记录和旧工作区：检查结果摘要保留后删除，不把临时日志作为最终报告的唯一证据。
- 已确认的源码缺陷及其修复/授权记录：独立保留在全局报告目录，由最终报告引用；不能当作已解决的工具错误一并清掉。
- 本轮未解决的问题或尚未完成的工作：保留记录及恢复所需输入，不以报告精简为由删除。

仅在工具确实需要机器可读的哈希或版本映射时另留 manifest；否则这些信息写入最终报告即可，不重复维护两套记录。历史版本通过项目版本管理追溯，不默认复制多份完整产物。记录安置、链接检查和删除时机统一按主 skill 的[收尾流程](../SKILL.md#全局一致性检查与收尾)执行。

## 各类报告

以下说明各类报告的用途与必要内容，不要求固定章节或空栏目。

### 设计说明

这份长期保留的说明让读者看懂本轮新增或修改的lib、spec和VC，并指出函数规格中需要人重点审阅的内容。

简单解释本轮新增或修改的内容在讲什么。标明本轮涉及的文件和符号，结合用途解释：

- **Lib**：新增定义、predicate、抽象操作或引理分别表达什么，为什么需要它们，怎样描述C对象、资源归属和状态变化，以及如何与已有定义和 `os_inv` 配合。修改已有定义时说明原来怎样、现在怎样、为什么改。
- **Spec**：本轮为哪些函数新写或修改了契约，它们描述的操作是什么，调用需要什么条件，成功和失败分别保证什么；指出规格与真实C路径的对应关系。
- **VC**：实际新增或修改的证明目标在证明什么，对应哪些C路径、调用或资源操作，关键证明如何借助本轮lib和spec完成。按有意义的证明问题归纳，重点解释关键义务和证明思路。

还需解释Spec中需要人重点审阅的内容。结合具体函数、条件或分支指出，比如入口限制了哪些输入和状态，是否排除了本应覆盖的情况；成功、失败和部分成功的保证是否符合预期；资源在caller、对象和 `os_inv` 之间如何交接；采用了哪些会影响结论的抽象、源码适配、假设或适用限制。解释这些点为什么值得确认，让读者知道应到哪份规格的哪一处看什么。（这些只是举例）

说明以本轮实际改动为范围，给出可定位的文件和符号链接；单纯复用的内容简要交代作用即可。篇幅按复杂度决定，不强制章节或表格，也不逐项抄写代码和VC。后续轮次补充新的改动及原因，保留仍有效的解释。

提交predicate/spec审阅及用户确认前，更新规格导读；进入实现阶段产生VC和证明后，再补充对应说明。仅设计任务说明已产生的lib/spec即可。审阅revision、通过结论及证明进度由审阅或验证结果记录，设计说明链接这些依据，并在实验完成后长期保留。

### 审阅报告

说明review了哪个版本、结论是什么；发现问题时，标出位置，解释哪里不一致、有什么影响以及如何确认修复有效。Predicate和spec分别给出结论，可写在同一份记录中，并引用同一份设计说明。

规格审阅记录区分本轮新写规格与导入契约，注明复用来源及已知证明状态；导入契约的未证或适配义务如实记录，供验证结果说明依赖条件。

原因尚不清楚时直接解释疑点及所缺依据。如果没有改变 predicate/spec 的含义，只是补充或调整证明步骤、修正工具用法，有必要时简要说明即可，不必另写报告。已有问题说明直接引用位置或 ID。

### 源码错误报告

发现C源码错误时，主动向用户说明，并在报告中写清：

- **哪里错了、为什么错。** 给出源码位置和适用配置，用具体输入或执行过程说明预期行为、实际结果及后果。
- **准备怎样修改。** 对照原代码和修改后代码，解释每处修改的原因，以及它如何解决问题。
- **实际处理情况。** 注明哪些修改已获用户同意、哪些已应用、哪些仍待处理；若通过增加假设继续验证，写清假设及其适用范围。
- **怎样检查的。** 记录针对性测试或反例、检查结果，以及验证针对的源码版本和修复副本。

每项问题分别记录原源码与验证副本的状态及解决依据：已修复的问题对照原代码和修改后代码、说明区别，状态写为“验证副本已修复，原源码缺陷仍存在”；查证并非缺陷的，注明源码/配置证据；尚未查证的疑点标为“待查证”。缺少修复检查、排除证据或获批适用假设的项，阻塞受影响的predicate/spec编写及后续验证，不能只列为“已知限制”后给出通过结论。

经用户确认的修复应用于验证工程annotated C副本，注释保留原出错代码，检查通过后继续受影响的设计和验证；原始源码仓库保持只读。通过获批假设继续时注明适用条件，问题状态仍区别于已修复。Predicate/spec、证明或工具自身的问题记入相应设计或审阅记录。

### 设计变更报告

用于说明已通过审阅或经用户批准的 predicate/spec 的含义发生的变化。尚未通过审阅的草案直接修改；仅调整文字、格式或证明步骤，不需要写设计变更报告。
说明为什么需要修改、原来如何描述、现在改成什么，以及影响哪些已有结论、需要重新审阅或运行哪些检查。改动的内容与原因更新到设计说明；审阅影响及待检查项记入审阅记录。

### 最终报告

引用 QCP controller 的实际状态及已有 final-check 结果，说明哪些目标已验证、哪些尚未验证及剩余限制，并给出 `verified|not-verified|partially-verified` 状态；未到 done 时如实说明尚未完成。到done后，记录全局lib、annotated C、VC/证明的当前版本及编译、引用、源码一致性检查结果。必要检查尚未完成时，不得报告整个流程已经结束。

VC证明完成后、最终记录整理前，在最终报告中附一项代码增量统计：对 `*_proof_manual.v` 和本轮修改/新增的 lib 文件，按文件列出新增、删除、净增行及两类合计，使用包含注释和空行的普通 diff。以修改前记录的实际版本为基线，新文件以空文件为基线；注明基线与统计终点，不将复制的原内容、未修改库或仅路径调整计入增量，共享文件只计一次。缺少可靠基线时明确说明，不能用 HEAD 代替未提交的原始内容或估算数字；新 manual 的模板行包含在文件增量中，不代表手写证明量。未完成时的统计标为阶段性数据，不另建统计报告。

最终完整性结论写入这份最终报告，不额外保留另一份重复的完整性报告。验证所需的审阅结论、trusted函数和全局假设在其中汇总，设计内容引用长期保留的设计说明，源码缺陷报告也保留；全局一致性确认与临时产物清理按主skill的[收尾流程](../SKILL.md#全局一致性检查与收尾)执行。
