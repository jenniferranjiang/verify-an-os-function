# 验证记录指南

报告首先写给用户看，其次才是留给工具和后续验证者的证据。以下是内容分类，不是每次任务都要生成的文件清单。按实际需要组织，可合并在同一文件中；优先更新已有内容，同一事实只记录一次。默认不使用模板、固定文件名或空栏目。

## 写作原则

面向熟悉 C 和目标模块、但未参与本次证明的读者，按当前要解释的设计或问题组织记录，并标明相关文件、函数或定义的位置。用自然语言说明这里做了什么、为什么这样设计，或发现了什么问题及其影响。尚未确定的内容直接说明哪里不清楚、缺什么依据、准备如何确认。

技术术语用于精确定位，不能代替解释。例如 ownership 要说明谁持有哪块内存、何时交出或收回；dependency closure 要说明此次修改具体影响哪些定义或调用者、为什么。不要只写“资源不闭合”“模型不一致”或“检查通过”，而不解释缺少什么、哪里不同或检查支持什么结论。

例如，假设审阅发现删除操作的内存归还没有被描述，与其写“lifecycle ownership 不闭合，需 invalidated dependency closure”，可以写：“删除函数会释放信号量对象，但当前描述没有说明该对象的内存如何归还给分配器，因此还不能用它验证删除操作。需要补充这一步资源转移，并重新检查依赖这一描述的删除函数约定。”这只是表达示例，不代表项目中存在该问题；实际记录还应附对应位置和证据。

位置可写成文件链接及行号，或文件路径和函数/定义名，可以适当引用源代码。这次审阅针对哪一份代码、哪些编译选项，以及哪一版 predicate/spec在结论处注明一次即可。


## 各类报告

以下说明各类报告的用途，不规定每份报告的章节或必填项。

### Predicate 设计报告

解释当前设计如何描述 C 对象的内存分布和行为，以及为什么这样组织。

### 审阅报告

说明review了哪个版本、结论是什么；发现问题时，标出位置，解释哪里不一致、有什么影响以及如何确认修复有效。Predicate 和 spec 分别给出结论，可写在同一份报告中。

原因尚不清楚时直接解释疑点及所缺依据。如果没有改变 predicate/spec 的含义，只是补充或调整证明步骤、修正工具用法，有必要时简要说明即可，不必另写报告。已有问题说明直接引用位置或 ID。

### 错误报告

仅记录当前配置下权威 C 源码本身的缺陷。Predicate/spec 写错、证明未完成、注解不足、编译或工具失败等验证过程中的问题，不属于此类报告。
指出源码位置，用具体触发场景解释预期行为、实际行为和后果，并附支持判断的执行路径或反例。
有修复建议或需要用户决定的事项时一并说明。未经用户授权不得修改权威源码。需要持续追踪时可使用 ID

### 设计变更报告

用于说明已通过审阅或经用户批准的 predicate/spec 的含义发生的变化。尚未通过审阅的草案直接修改；仅调整文字、格式或证明步骤，不需要写设计变更报告。
说明为什么需要修改、原来如何描述、现在改成什么，以及影响哪些已有结论、需要重新审阅或运行哪些检查。相关内容可写在已有报告中，不必单独新建文件。

### 最终完整性检查报告

引用 QCP controller 的实际状态及已有的 `final-check` 结果，说明哪些目标已验证、哪些尚未验证及剩余限制，并给出对应的 `verified|not-verified|partially-verified` 状态；未到 `done` 时如实说明尚未完成。切片与原源码一致性引用仍然有效的 Spec 审阅结论；相关错误、待批准的设计变更或其他阻塞问题直接引用已有说明。不另执行一套最终证明检查，也不重复诊断历史。

只有必需检查通过，且不存在与批准目标冲突的未解决源码错误或未批准设计变更时，才能标为 `verified`。仅编译通过或用户接受某个问题，不代表已经完成所要求的验证。
