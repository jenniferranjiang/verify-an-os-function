- 是否存在剩余 blocker 或不确定性；
- 已确认新 trial 没有依赖旧 trial的证据。

# 十二、历史诊断基线

旧实验的用户提供基线为：

- 172/172 个正式 VC；
- 124 个 verified-auto Qed；
- 48 个 direct manual obligations；
- 九个 verified goal-check；
- 全量 Rocq 编译；
- 全量 coqchk；
- trust scan 无本实验新增的不可信公理；
- manual/verified proof 不依赖原 generated-auto placeholders。

这些数字只作为诊断基线。

必须以本次实际生成的 goals 和 dependency closure 为准。如果数量不同，必须定位并解释原因；
不得为了匹配历史数字而删除、合并、隐藏或弱化 VC。

不得读取旧 trial 来比较这些数字或寻找历史 proof。

# 十三、框架 trust base

允许使用当前 QCP/Rocq 工程正常依赖的既有框架 trust base，例如：

- sizeof_front_end_type；
- eval_addr_expr；
- Rocq/Coq 标准库所需的经典逻辑或外延性；
- QCP 已有 parser、symbolic executor 和验证框架接口。

这些不是本实验新增的用户公理。

不得把本次新建的 Parameter、Axiom、Admitted、admit 或占位 definition
伪装成框架既有 trust base。

# 十四、唯一允许暂停的条件

只有以下情况才停止并请求用户输入：

- 当前权威源码或配置与第三节固定目标实质不一致；
- 完整闭包需要新增或替换 trusted symbol；
- 必须实质改变第五节批准的 predicate 语义目标；
- 必须实质改变第六节批准的函数行为目标；
- 发现权威 C 缺陷，且完成证明必须修改真实 C 行为；
- dispatch、宏、类型布局或 ABI 无法从权威源码/config 唯一确定；
- 必须修改或晋升根共享 lib；
- verification-orchestrator 返回无法在当前授权范围内解决的明确 blocker；
- 必需文件、工具或执行权限不可用，并且安全的范围内替代方案已经耗尽；
- Goal 被用户暂停、系统中断或达到系统预算限制。

阶段完成、生成新 revision、一次失败、夜间无人值守或通常的 predicate/spec 确认门，
都不是暂停理由。

停止时必须留下可恢复状态，并报告：

- 已完成阶段；
- 当前 source/predicate/spec revisions；
- 精确 blocker；
- file/symbol/command 证据；
- 已尝试路径；
- 为什么不能在当前授权范围内继续；
- 恢复所需的最小用户输入；
- 下一条应执行的具体命令或 controller action。

除上述情况外，持续执行，直到 final integrity 完成并有机器检查证据支持。
